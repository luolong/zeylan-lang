:navtitle: The Zeylan Language Environment

[quote, Zeylan Design Group, 2026]

We wanted a programming language that reflects how modern network software is actually written, not how we were forced to write it in the 1990s.

== Executive Summary

In 1995, the Java team released a white paper describing a language designed to resolve the headaches of the time—namely, manual memory management, pointer bugs, and compile-once-run-nowhere build issues in C and C++.
Java achieved this by bringing object-oriented programming to a safe, garbage-collected virtual machine, establishing the foundation for thirty years of enterprise software engineering.

Today, software development has entered a new era.
We no longer write monoliths on single machines; we build distributed, microservice-based systems that rely heavily on third-party package registries, asynchronous networking, complex dependency injection (DI) containers, and pervasive observability tracing. 

Yet our programming languages are still fighting the battles of the past.
To build modern cloud-native systems, developers are forced to write massive amounts of boilerplate and run-time "magic" (such as reflection, annotations, and thread-local variables) to bypass language limitations.

*Zeylan* is designed to solve the problems of the modern cloud-native era.
By evolving Ceylon’s set-theoretic type system and combining it with a compiler-tracked *algebraic effect system*, Zeylan delivers:

1. *Elimination of the "Colored Function" Problem*: Write non-blocking, asynchronous code with standard, clean, synchronous syntax.
2. *Compiler-Enforced Dependency Injection*: No reflection, no runtime DI containers, and trivial mocking without bloated interfaces.
3. *Secure-by-Default Sandboxing*: Third-party modules are completely sandboxed by the compiler and cannot access disk, network, or env variables unless explicitly granted.
4. *Thread-Safe Scoped Context*: Say goodbye to fragile thread-locals and context-drilling.

Zeylan delivers these advancements without requiring complex functional programming paradigms.
It remains familiar, object-functional, and pragmatic.

== The Key Design Pillars of Zeylan

The following sections detail the architectural pillars of the Zeylan environment.

=== 1. Side-Effects by Default, Opt-In Purity

For decades, the programming language community has split into two camps:

* *The Imperative/Pragmatic Camp*: Languages like Java, Go, and TypeScript make side-effects implicit.
You can print, write to databases, or query APIs anywhere.
However, this makes functions unpredictable, hard to test, and impossible for the compiler to optimize safely (e.g., through concurrency or memoization).
* *The Pure Functional Camp*: Languages like Haskell or Scala (using Cats Effect/ZIO) enforce strict purity.
Side-effects must be wrapped in `IO` monads, forcing developers to write in monadic styles, handle complex type signatures, and explain why a log statement requires a complete rewrite of a function's return type.

Zeylan resolves this tension through **opt-in purity and automated effect inference**.

* **Standard code requires no annotations:** Functions can perform side-effects naturally.
The compiler automatically infers what external operations a function performs.
* **Opt-in `pure` keyword:** For performance-critical code, core business logic, or mathematical operations, you can mark a function as `pure`.
+
[source,ceylon]
----
shared pure Float calculateTax(Float amount, Float rate) => amount * rate;
----
+
The compiler guarantees that a `pure` function does not perform side-effects.
It can be cached, parallelized, or executed concurrently without lock contention.

=== 2. Unified Control Flow (Eliminating the "Colored Function" Split)

In modern web systems, database queries and network calls must be non-blocking.
To achieve this, languages like JavaScript, Rust, C#, and Python introduced `async`/`await`. 

However, this split codebases in two:

* A synchronous function cannot call an asynchronous function without blocking a thread or changing its signature to return a `Promise`/`Future`.
* Once a helper function is marked `async`, every caller up the stack must also be marked `async` (the "colored function" problem).
* Code gets littered with `await` keywords, making control flow noisy and prone to subtle concurrency bugs (e.g., forgetting to await a call).

Zeylan eliminates the async/await distinction.
Under the hood, asynchronous scheduling, exception handling, and generator iteration are all unified under one native language feature: **Algebraic Effects**.

[source,ceylon]
----
shared UserProfile getProfile(String userId) performs Database | Logger {
    Logger.info("Fetching profile for " + userId);
    value user = Database.findUser(userId);
    return UserProfile(user.name, user.email);
}
----

Notice that `Database.findUser` is non-blocking and executes asynchronously, but there is no `async` or `await` keyword.
The compiler knows this function requires the `Database` and `Logger` capabilities.
If those capabilities are implemented using non-blocking asynchronous runtimes, the runtime handles suspending and resuming the function's execution transparently.
The developer writes clean, sequential, synchronous-looking code.

=== 3. First-Class Handlers (Boilerplate-Free Dependency Injection)

In modern enterprise architectures, code must be decoupled from concrete systems.
We define interfaces like `UserRepository` so we can swap out a real database for an in-memory database during unit testing.
To manage these implementations, we rely on heavy dependency injection (DI) frameworks (like Spring Boot, Guice, or NestJS) which use reflection, slow down application startup, and make stack traces unreadable.

In Zeylan, dependency injection is a compiler-enforced language feature. 

1. **Declare Capabilities**: Functions list the capabilities they perform (`performs Database | Logger`).
2. **Decouple Implementation**: Functions do not instantiate their dependencies.
3. **Handle at the Boundary**: The caller specifies how to resolve the capabilities.

[source,ceylon]
----
shared void runApplication() {
    value realDb = PostgresDatabase("jdbc:postgresql://...");
    value systemLogger = ConsoleLogger();

    // Bind capabilities to concrete instances at the application root
    handle {
        value profile = getProfile("user_123");
        print("User profile email: " + profile.email);
    } with {
        Database => realDb;
        Logger   => systemLogger;
    };
}
----

For testing, you swap the handler implementation instantly, with no frameworks required:

[source,ceylon]
----
shared void testGetProfile() {
    value mockDb = InMemoryDatabase();
    value silentLogger = NoOpLogger();
    
    value profile = handle {
        getProfile("user_123");
    } with {
        Database => mockDb;
        Logger   => silentLogger;
    };
    
    assert(profile.name == "Test User");
}
----

Because capabilities are tracked by the compiler, if you add a new capability requirement deep in the system, the compiler will tell you exactly where it is unhandled, preventing runtime "missing bean" errors common in traditional DI frameworks.

=== 4. Zero-Trust Sandboxing (Supply Chain Security)

Modern applications pull in thousands of transitive dependencies from NPM, Cargo, or Maven.
If a single dependency is compromised, a malicious library can read environment variables (stealing private keys) and send them to a remote server. 

Runtime sandboxing (like in Node.js or JVM SecurityManager) has either been deprecated due to performance costs or is too coarse-grained to be useful.

Zeylan moves security policies to compile-time capabilities:

* **Zero access by default:** By default, third-party libraries have *no* permission to access environment variables, read/write files, or open sockets.
* **Capabilities are explicit:** Accessing the file system is just another algebraic effect (e.g., `FileSystem`).
A library cannot perform this effect unless you explicitly grant it in your module's configuration or handle it with an approved system handler.
* **Safe dependency composition:** You can import a library for JSON parsing and rest easy knowing the compiler guarantees it cannot make network requests—because its signature doesn't declare the `Network` effect, and the compiler would reject it if it tried.

=== 5. Dynamic Context Propagation (Observability & Tracing)

Passing request-scoped data—such as request IDs, JWT user sessions, database transaction boundaries, or zipkin trace spans—through a call stack is a common challenge in microservices:

* **The "Context Drilling" approach** (common in Go) requires adding a `ctx` argument to every single function signature in the system, cluttering business logic.
* **The "Thread-Local" approach** (common in Java/Spring) stores context in a thread-bound variable.
However, this breaks as soon as execution moves across thread pools, reactive streams, or event loops, leading to lost trace IDs and debugging nightmares.

Zeylan offers **Implicit Scoped Context**.
Since context variables are modeled as algebraic effects, they bubble down implicitly.
Any child function can read the request context type-safely, and the compiler guarantees that the context propagates seamlessly across async boundaries, thread transitions, and event loops.

=== 6. First-Class Durable Workflows (Fault-Tolerant Distributed Orchestration)

Orchestrating long-running, multi-step business logic (such as order fulfillment, user onboarding, or payroll processing) is exceptionally difficult.
If a server crashes midway through a three-day process, the system must recover its exact state and resume execution without losing progress or executing duplicate steps.

To solve this today, developers use:

* **Database State Machines**: Manually storing status columns, managing step queues, and writing complex polling logic.
* **External Orchestration Engines**: Frameworks like Temporal or Cadence that use event-sourcing and code replay.
While powerful, these frameworks require workflows to be strictly deterministic.
If a developer accidentally calls a non-deterministic API—such as getting the current system time (`Instant.now()`), generating a random UUID, or accessing the file system—the compiler cannot detect it.
The workflow will compile successfully, only to fail unpredictably at runtime during replay.

Zeylan solves this by combining **algebraic effects** with its **capability type system**:

1. **Delimited Continuations as Serializable State**: Because Zeylan's algebraic effects are modeled as delimited continuations, the running execution stack of a workflow can be paused, serialized, saved to a database, and resumed later on a completely different machine in the cluster when a wake-up event occurs.
2. **Compile-Time Determinism Checking**: The compiler ensures that a workflow function only performs deterministic operations.
By checking the capability requirements, the compiler guarantees that a function requiring `performs Workflow` cannot directly perform side-effects like file access, system time queries, or network requests unless those are routed through safe, tracked activity boundaries.

[source,ceylon]
----
// A durable workflow whose determinism is fully guaranteed by the compiler
shared void processOrder(String orderId) performs Workflow {
    Workflow.info("Starting order process for " + orderId);
    
    // Durable execution of an external activity (tracked and logged)
    value paymentResult = Workflow.executeActivity(chargePayment, orderId);
    
    if (paymentResult.success) {
        // Durable sleep: execution is paused, serialized to DB, and resumed in 3 days
        Workflow.sleep(Duration.days(3));
        
        value shipped = Workflow.executeActivity(shipItems, orderId);
        Workflow.info("Order shipment status: " + shipped.toString());
    }
}
----

Because execution pauses and yields resources naturally, a cluster of Zeylan applications can run millions of concurrent long-running workflows with negligible memory overhead.

== Summary: The Zeylan Value Proposition

[cols="1,2,2", options="header"]
|===
| Pain Point | Existing Solutions | The Zeylan Solution

| **Async/Sync Divide**
| `async/await` syntax, colored function split, codebase duplication.
| Unified algebraic effects. Clean, sequential code with non-blocking async runtimes.

| **Dependency Injection Boilerplate**
| Heavy DI frameworks, runtime reflection, interfaces written purely for mock testing.
| First-class handlers. Compile-time checked, boilerplate-free mapping of capabilities.

| **Supply Chain Security**
| Coarse container-level isolation, post-facto security scanning.
| Zero-trust compiler capability tracking. Third-party packages are sandboxed by default.

| **Tracing & Context Drilling**
| Fragile `ThreadLocal` / `AsyncLocalStorage`, or boilerplate `Context` arguments.
| Ambient context tracked by the compiler, propagating safely across all execution boundaries.

| **Durable Orchestration**
| Complex manual state machines, or orchestration engines with runtime-only determinism checks.
| Native delimited continuations. Persistable, serializable code flow with compile-time deterministic constraints.
|===

By addressing the real-world headaches of the modern developer—concurrency, composition, testing, and security—Zeylan makes building large-scale distributed applications robust, secure, and productive.
